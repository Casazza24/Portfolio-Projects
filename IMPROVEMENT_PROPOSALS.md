# Portfolio Improvement Proposals

Status: proposal only. Nothing in this document has been implemented. It is a discussion draft for deciding what to build next across the Phase 3 dashboards and the portfolio website.

Scope note: the portfolio website (Next.js, React, TypeScript, Tailwind, deployed on Vercel) lives in a separate repository, `Personal-Website`, not in this monorepo. Proposals that touch the website describe changes to make there, not here.

---

## Section 1: Phase 3 Demo Visual Improvements

### 1.1 Current state of the two existing dashboards

Both `consumer-credit-risk-analytics/dashboard.html` and `nyc-transit-efficiency-analysis/dashboard.html` are generated by a `build_dashboard.py` script that reads CSV outputs (or, for transit, recomputes the frames directly from raw CSVs) and writes a single self-contained HTML file with Plotly charts and client-side tab navigation. Neither uses a JS framework; both are plain HTML/CSS/JS strings assembled in Python f-strings. This makes them easy to regenerate but means every styling change has to happen inside the Python string templates, not in a separate stylesheet.

The two dashboards do not currently share a design system, even though they are meant to sit side by side in the same portfolio:

- **Credit risk dashboard** (`build_dashboard.py`, `generate_html()`, lines 226-276): light theme, background `#f8f9fa`, a flat dark slate header (`#2c3e50`) with no gradient, system-font stack, an underline-style tab bar (`.tab-bar` / `.tab-btn` with a bottom border on the active tab) rather than pill buttons, no card wrapper around each chart, just `.tab-content { padding: 20px }` directly holding the Plotly div. It inlines `https://cdn.plot.ly/plotly-2.35.2.min.js` from Plotly's own CDN, and because it does not pass `include_plotlyjs` selectively, the resulting `dashboard.html` is 6.4 MB on disk in this checkout (the JSON trace/layout data is inlined into `<script>` tags per tab rather than referencing a shared data source).
- **Transit dashboard** (`build_dashboard.py`, `build()`, lines 199-246): already a step ahead stylistically. It uses CSS custom properties (`--brand`, `--brand-dark`, `--ink`, `--muted`, `--line`, `--bg`, `--card`), a light blue-gray background (`#eef1f6`), a gradient header (`linear-gradient(135deg, var(--brand-dark), var(--brand))`), pill-shaped tabs with hover/active states and shadows, and a `.card` wrapper (white background, rounded corners, subtle box-shadow) around each chart. It also loads Plotly once from CDN on the first tab only (`include_plotlyjs=("cdn" if i==0 else False)`), which the code comments note shrinks the file from ~4.9 MB to ~50 KB. Its header already includes a one-line project description under the title (`<p>` under `<h1>`), which the credit risk dashboard lacks entirely (its header is just an `<h1>` and one static tagline, `<p>Lending Club loan default prediction...</p>`, with no date range or dataset framing).

So concretely: the transit dashboard is the better base pattern (CSS variables, cards, pill tabs, lighter file), and the credit risk dashboard needs the most work (no cards, no CSS variables, no gradient header, 6.4 MB file size from unoptimized Plotly loading). Neither is dark-themed; both currently use light backgrounds (`#f8f9fa` and `#eef1f6`) that clash with the portfolio site's dark scheme, and neither dashboard is linked from a live "Demo" button today (see Section 2.4).

### 1.2 Proposed color scheme alignment

Adopt a shared dark palette as CSS custom properties at the top of both templates (this only requires editing the `<style>` block strings in each `build_dashboard.py`, no change to the chart-building functions):

```
--bg: #0f1420          (page background, near-black navy)
--card: #171d2b         (card background, one step lighter than bg)
--card-border: #2a3346   (hairline border on cards)
--ink: #e6e9ef           (primary text, near-white)
--muted: #94a3b8         (secondary text, captions, footer)
--brand: #4C72B0         (existing chart blue, kept as-is so chart colors and UI accents match)
--brand-dark: #33507e
--accent: #DD8452        (existing chart orange, used for secondary accents/hover states)
```

Reusing `#4C72B0` (`BLUE`) as the brand accent is deliberate: it is already the primary series color in both `build_dashboard.py` files' chart palettes (`BLUE, ORANGE, RED, GREEN, TEAL` constants), so the UI chrome and the data series would use the same blue rather than introducing a mismatched accent color. Plotly's `template="plotly_white"` (set in the transit dashboard's `build()`, line 203) would need to change to a custom dark Plotly template, or at minimum override `paper_bgcolor`/`plot_bgcolor` to `var(--card)`'s hex value and set `font.color` to the light ink color, axis line/gridline colors to a muted slate, so chart backgrounds do not stay white inside a dark page.

### 1.3 Typography

Both dashboards currently use a system-font stack (`system-ui, -apple-system, 'Segoe UI', Roboto, sans-serif` for transit; `-apple-system, BlinkMacSystemFont, "Segoe UI", Roboto, sans-serif` for credit risk). Keep the system-font approach (it avoids a webfont network request in a file meant to be a lightweight static demo) but standardize on one stack across both files, and add a clearer type scale so headers, tab labels, and captions are visually distinct rather than close in size:

- Dashboard title (`h1`): 26-28px, weight 650-700
- Subtitle/description paragraph: 15px, `--muted` color, max-width capped (transit already does `max-width: 70ch`; carry this to credit risk, which currently has no width cap on its header paragraph)
- Tab labels: 14px, medium weight
- Chart titles: rely on Plotly's own title sizing but set `font.size` explicitly (currently unset, so it falls back to Plotly defaults) to roughly 16-18px so it does not visually compete with the page's `h1`
- Footer/caption text: 12-13px, `--muted`

### 1.4 Card-based section layout

Transit already wraps each chart in a `.card` div (`build()`, line 209-211: `<div class="card">{div}</div>`). Extend the same `.card` class definition to the credit risk dashboard's `.tab-content` blocks in `generate_html()` (currently just a bare padded div with no border, background, or shadow). Concretely, in `consumer-credit-risk-analytics/build_dashboard.py`, wrap the `<div id="chart-{i}">` in a `<div class="card">...</div>` the same way transit does, and add the `.card{background:var(--card);border:1px solid var(--card-border);border-radius:14px;padding:16px 18px;box-shadow:0 4px 20px rgba(0,0,0,.3)}` rule (shadow darkened relative to transit's light-theme version since a dark card needs a stronger shadow to read as "raised").

### 1.5 Chart styling

For both dashboards, pass an explicit dark Plotly layout template so individual chart-building functions (`build_grade_chart`, `build_roc_chart`, `build_importance_chart`, `build_dti_income_chart`, `build_time_series` in credit risk; `fig_dow`, `fig_month`, `fig_rain`, `fig_temp`, `fig_regression`, `fig_delays` in transit) do not each need per-chart edits. The transit `build()` function already has a single central point where this can be added (line 203: `fig.update_layout(template="plotly_white", ...)`), swap `"plotly_white"` for a custom dark template or `"plotly_dark"` as a starting point, then override `paper_bgcolor`/`plot_bgcolor` to transparent so the card background shows through (both already set to `rgba(0,0,0,0)`, which is correct and can stay). Credit risk's `generate_html()` builds layout dicts per-chart with no shared post-processing step; the simplest fix is to inject a shared `"template": "plotly_dark"` (or explicit dark color overrides) into every `layout` dict right before `json.dumps(layout)` in the `tab_divs.append(...)` loop, rather than editing five separate chart functions.

### 1.6 Adding a project title/description header to each dashboard

Transit's header (line 233-234) already contains a real description: `<h1>NYC Transit Efficiency Analysis</h1>` plus a `<p>` describing the question, date range, and headline finding. Credit risk's header (line 254-255) only has the title and a one-line tagline with no date range, dataset size, or headline finding. Bring credit risk's header up to the same standard, for example: "Lending Club loan default prediction on 2.2M peer-to-peer loans (2007-2018 vintage) comparing Logistic Regression against XGBoost. XGBoost meaningfully outperforms the baseline; DTI and revolving utilization matter more than raw income." This mirrors the pattern of stating the headline finding directly in the header, which transit already does and which reads well as a presentation-ready summary before a viewer has looked at a single chart.

### 1.7 Grid Energy Demand Forecasting: no dashboard.html exists

Confirmed: `grid-energy-demand-forecasting/` has no `build_dashboard.py` or `dashboard.html`. Its `analysis.py` produces static Matplotlib PNGs and CSVs into `outputs/` (per its own docstring: `feature_importance.png`, `actual_vs_predicted.png`, `residuals.png`, `ablation_comparison.png`, `model_metrics.csv`, `feature_importances.csv`, `predictions_sample.csv`) plus a Tableau-ready CSV (`data/pjm_predictions.csv`). There is a separate `spectral_analysis.m` for the MATLAB FFT work and a `generate_mock_spectral.py` fallback, but nothing produces an interactive HTML artifact today. This is the one Phase 3 project without a live-explorable demo, and it is also the only one of the three with a distinct second-language angle (MATLAB spectral analysis) that a static PNG cannot show off interactively.

Proposal: add `grid-energy-demand-forecasting/build_dashboard.py` following the same pattern as the other two, reading from `outputs/` and `data/`. Concrete tabs to surface, mapped to what `analysis.py` already produces or could easily be adapted to export as CSV (the two existing scripts already save all data used for their Plotly charts as CSV alongside PNGs, so parity is just a matter of adding equivalent CSV exports where analysis.py currently only saves PNGs):

1. **Actual vs. predicted demand** (time series line chart, replacing `actual_vs_predicted.png`) with a zoomable date range, since this is the chart that most benefits from interactivity versus a static PNG.
2. **Feature importance** (horizontal bar, replacing `feature_importance.png`), same chart type and layout convention as credit risk's `build_importance_chart`.
3. **Ablation comparison** (grouped bar: with-spectral vs. without-spectral MAPE/RMSE, replacing `ablation_comparison.png`) since this is the project's central thesis per its WRITEUP.md ("The ablation study is the project's thesis statement") and deserves to be the most prominent, not a secondary static image.
4. **Demand heatmap** (hour-of-day by day-of-week or hour by month, mentioned in the WRITEUP as "The demand heatmap reveals the expected pattern: weekday peaks during business hours... with summer afternoon demand substantially higher than winter" but not listed among analysis.py's current output files, so this would need a new chart function).
5. **Spectral power spectrum** (if `spectral_analysis.m` or `generate_mock_spectral.py` outputs are exposed as a CSV of frequency vs. power, this would visually anchor the FFT-based feature engineering story that is otherwise only described in prose in the WRITEUP).

This keeps the three Phase 3 projects consistent: same build script pattern, same shared color constants (`BLUE, ORANGE, RED, GREEN` already defined at the top of `grid-energy-demand-forecasting/analysis.py`, reusable directly in a new `build_dashboard.py`), same dark theme once 1.2-1.5 are applied.

### 1.8 "About This Project" expandable section from WRITEUP.md

All three projects already have a WRITEUP.md with a consistent structure (problem statement, data/methodology, key findings, tools/stack). Proposal: at the top of each dashboard, below the header and above the tab bar, add a collapsed `<details>`/`<summary>` HTML element (native browser disclosure widget, no JavaScript required beyond what is already inline) titled "About This Project," pre-populated with a condensed version of that project's WRITEUP.md:

- A one-paragraph problem statement (e.g., credit risk's "Every lending decision is a bet... this project builds a default prediction pipeline on Lending Club's historical loan dataset").
- 2-4 bullet "Key Findings" pulled near-verbatim from the WRITEUP's Key Findings section (e.g., transit's "calendar structure drives NYC subway ridership; weather only trims the edges" or credit risk's "DTI and revolving utilization matter more than income").
- A "Tools and Technologies" line (each WRITEUP already has this as its own section, so it is a direct copy).

Mechanically, since `build_dashboard.py` already runs in Python at generation time, this content can either be hand-copied into a constant string in each `build_dashboard.py` (simplest, but drifts from WRITEUP.md if the writeup changes later) or read directly from `WRITEUP.md` at build time using a small Markdown-to-HTML step (adds a dependency, e.g. `markdown` or `python-markdown2`, to `requirements.txt`, but stays in sync automatically). Given these are static, rarely-revised writeups, the simplest hand-copied approach is likely sufficient and avoids adding a new dependency to three `requirements.txt` files for a section that will not change often.

## Section 2: Additional Recommendations

### 2.1 Dark/light mode toggle on the portfolio site

Recommendation: skip it, at least for now. The site is already committed to a dark theme as its identity (per the brief, "dark color scheme" is the current design), and a toggle adds real implementation cost (a theme context, `prefers-color-scheme` detection, persisting the choice, and auditing every component for light-mode-safe contrast) for a personal portfolio that most visitors will view once. This is time better spent on the Phase 3 dashboard work in Section 1, which visibly upgrades the three flagship projects a hiring manager will actually click into. If a toggle is added later, it is far cheaper to do once the component library is stable than to retrofit now.

### 2.2 Project screenshots or thumbnails on project cards

Recommendation: do this, and prioritize it above the dark/light toggle. Looking at `components/ProjectCard.tsx` in the website repo, every card currently renders the same generic treatment: a 160px-tall `bg-gradient-to-br from-blue-100 to-indigo-200` block with a single FontAwesome icon centered in it (`h-40 bg-gradient-to-br ... <FontAwesomeIcon icon={project.icon} .../>`). All eight project cards look structurally identical except for which icon appears, which does not differentiate a dashboard-driven data project from a full-stack app from a group hackathon project. A static screenshot or short auto-playing GIF of the actual dashboard (once Section 1's dark-theme work is done, these screenshots would also visually match the site) replacing that gradient-plus-icon block would immediately make the credit risk, transit, and grid energy cards look like real, working products rather than placeholders. This is a moderate-effort, high-visual-payoff change: take one screenshot per project's dashboard.html or notebook, drop into `public/images/`, add an `imageUrl` field to the `Project` interface in `data/projects.ts`, and update `ProjectCard.tsx` to render an `<img>` instead of (or as a background under) the gradient block.

### 2.3 Analytics snippet (Vercel Analytics)

Recommendation: add it. Since the site is already deployed on Vercel, Vercel Analytics is close to a zero-cost addition (`npm install @vercel/analytics`, drop `<Analytics />` into `app/layout.tsx`, enable it in the Vercel project dashboard). It costs nothing to add, has no visual footprint, and gives concrete signal on which projects recruiters or hiring managers actually click into, which is directly useful feedback for deciding where to invest further polish (for example, confirming whether the Phase 3 dashboards in Section 1 are worth the additional build-out effort, or whether a different project draws more traffic).

### 2.4 GitHub Pages for live Phase 3 dashboard demos

Recommendation: do this, it closes a real, currently-visible gap. Looking at `data/projects.ts` in the website repo: Consumer Credit Risk Analytics, Grid Energy Demand Forecasting, and NYC Transit Efficiency Analysis all have `demoUrl: null`, so their "Live Demo" buttons render as disabled, grayed-out spans on the live site (`ProjectCard.tsx` line 53-61, the `aria-disabled="true"` branch with `title="Demo coming soon"`). Meanwhile Stock Prediction ML already has a working `demoUrl: 'https://casazza24.github.io/stock-prediction-ml-/'`, proving the GitHub Pages pattern is already in use elsewhere in this same portfolio, just not extended to the three Phase 3 projects that would benefit most (they are the projects with genuine interactive dashboards, unlike the group/hackathon projects that have no demo at all). Concretely: enable GitHub Pages on the `Portfolio-Projects` repo (or a dedicated pages branch), serve each dashboard at a subpath like `https://casazza24.github.io/Portfolio-Projects/consumer-credit-risk-analytics/dashboard.html`, and update the three `demoUrl` fields in `data/projects.ts` accordingly. The one caveat: the credit risk `dashboard.html` is currently 6.4 MB (see 1.1), which is a poor experience to serve over GitHub Pages; doing the Plotly CDN-loading optimization described in 1.1 (matching what transit's `build_dashboard.py` already does, shrinking ~4.9 MB to ~50 KB) should happen before or alongside standing up Pages, not after.

### 2.5 Move or archive the legacy Casazza24.github.io folder

Recommendation: archive it out of this monorepo. `Casazza24.github.io/` is 6.4 MB, contains a self-contained old static site (`index.html`, `projects.html`, `resume.html`, `hobbies.html`, a `resources/` folder), and per this monorepo's own README.md is explicitly "retained for reference only" and "predates this repository's project structure." The current live site is the separate Next.js `Personal-Website` repo, so this folder serves no active purpose in `Portfolio-Projects` beyond historical reference, and its presence could confuse anyone (recruiter, collaborator) browsing this repo into thinking it is a second, competing version of the live site. Two reasonable options: (a) move it to a separate `Casazza24.github.io` GitHub repo dedicated to archival (this also happens to be the correct repo name for it to actually function as a GitHub Pages user site, if that is ever wanted again) or (b) delete it from the working tree and rely on git history if it is ever needed again. Given it is only 6.4 MB and already documented as legacy, either is low-risk; moving it to its own repo is the cleaner option since it preserves the folder as a runnable artifact rather than burying it in history.

### 2.6 Custom domain instead of the Vercel random-slug URL

Recommendation: do this, it is a small cost for a real credibility signal. `casazza-personal-website-ten-peach-66.vercel.app` reads as an auto-generated placeholder, which undercuts an otherwise polished portfolio the moment someone glances at the URL bar or pastes the link into an email or resume. A domain like `matthewcasazza.com` or `mattcasazza.dev` is inexpensive (roughly $10-20/year), and Vercel's custom domain setup is a few DNS records plus a click in the project settings; the memory notes the site is already on Vercel with env vars configured, so this is a low-friction addition, not a restructuring. This also gives a stable link to put on a resume or LinkedIn that will not look dated the way a Vercel-generated slug does.

### 2.7 Other improvements for a trading desk or data engineering hiring manager

- **Surface data volumes and quantitative rigor higher up.** The project card descriptions already contain strong quant signals ("2.2M Lending Club loans," "FFT," "Avellaneda-Stoikov framework") but a hiring manager scanning quickly benefits from these being visually distinct, e.g., a small stat row on each card (rows count, R-squared, AUC) rather than buried mid-sentence in the description paragraph. This pairs naturally with the card redesign in 2.2.
- **A quant-specific landing signal for RL Bond Market Making.** This project (Avellaneda-Stoikov market making, TensorFlow and PyTorch implementations) is the single most relevant piece for a trading desk audience specifically, more so than the DS/ML projects. Confirm it is positioned prominently (it is currently first in `data/projects.ts`, which is good) and consider whether its writeup surfaces Sharpe ratio, P&L, or inventory-risk metrics as concretely as the other three writeups surface AUC/R-squared/MAPE, since that is the language a trading-desk reviewer will scan for first.
- **Consistency of writeup depth.** The three Phase 3 WRITEUP.md files are all strong (clear problem framing, honest limitations sections, specific numbers). Confirm `rl-bond-market-making` has a comparably rigorous writeup, since it is arguably the highest-signal project for the stated audience and should not be the thinnest one.
- **Load time honesty check after Section 1 changes.** If dark-theme Plotly templates and CSS card layouts are added per Section 1, re-verify each dashboard's file size and load time before publishing live demo links (2.4), since a slow-loading demo undermines the "polished, presentation-ready" goal the visual overhaul is meant to achieve.
